# 개인 계좌·송금 정보 구현 대조

정본은 POLICY P09(가입 소셜+SMS, 계좌 등록 때 별도 예금주 확인), P10(송금 캡처·개인정보는 당사자/처리 담당자), P07(탈퇴·담당 인계 뒤 기존 금융 의무 접근 유지)다. 이슈12/14/16의 보관계좌만으로는 개인 환불과 선지출 반환의 실제 송금 정보를 제공할 수 없다. 초기 기본503에서 누락됐던 CODEF 예금주+1원 코드 인증을 [후속 명세](BANK-VERIFICATION.md)로 구현했다. 현재 전체 서버196/앱101을 검증했고, 실제 공급자 계약/키·기관코드·실계좌 수락은 별도다.

1. 개인 계좌 등록·교체: 본인 ACTIVE 세션, 업무 멱등키와 version, 은행·계좌번호·예금주 필수. 공급자 소유 확인 성공 뒤에만 VERIFIED를 저장한다. 실패/미설정은 기존 검증 계좌를 변경하지 않는다. 원문 계좌·예금주는 기존 BankData의 AES256-GCM으로 암호화한다.
2. 본인 계좌 조회는 마스킹·검증 상태·수정 버전만 반환한다. 서비스 닉네임과 예금주명을 혼용하지 않는다. 계좌 변경 이력은 기존 지급 사실을 다시 쓰지 않는다.
3. 전체 계좌는 정확한 납부/환불/선지출 반환의 송금 당사자에게만 제공한다. 모임 부원이라는 사유만으로 공개하지 않고 각 요청의 현재 상태·현재 담당자·해당 납부자/수령자를 확인한다. 탈퇴/차단은 기존 금융 관계를 지우지 않는다.
4. 내부 송금 안내에는 검증 계좌 ID/버전과 예금주를 표시하되 외부 송금 성공을 가장하지 않는다. 실제 은행 거래 식별은 공급자 계약상 계좌별 식별 범위와 맞춰야 하며, 서로 다른 계좌의 같은 텍스트 reference를 전역 중복으로 취급하지 않는다.
5. 해찬 docs/external/codef.md의 CODEF 예금주명+1원 이체/서버 코드 대사가 기존 설계다. 공급자 이름을 다시 묻지 않고 이를 현재 소셜+SMS 정책에 맞게 구현했다. 비밀키는 대화/Git에 넣지 않으며 실제 상품 승인·키·기관코드·실계좌 수락은 운영 환경에서 별도로 검증한다.

예정 증거: 계좌 등록 성공/실패·기존 계좌 보존·기밀값 저장/응답 분리·멱등 재시도/충돌·타인 조회 거절·납부/환불/인계 후 송금 맥락 접근. 실제 실패 테스트 확인 후 production 구현하고 결과를 REQUIREMENTS-AUDIT.md에 연결한다. 이 계획만으로 개인 계좌 구현 완료를 주장하지 않는다.
