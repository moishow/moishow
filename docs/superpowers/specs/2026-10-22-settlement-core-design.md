# 정산 계산 코어 설계 — 이슈 #11

## 사용자 의도와 범위

확정된 정책으로 곧바로 앱을 구현할 수 있도록 문서·화면·금액 예제를 맞추고, 첫 이슈에서 금액 계산을 실행·테스트한다. 사용자는 정책을 승인하고 이슈 브랜치에서 계획·구현을 진행하도록 요청했다. 실행은 이 채팅에서 직접 수행한다.

## 구조 선택

선택: Node 22+와 브라우저가 함께 불러오는 의존성 없는 ESM 순수 모듈. 기존 저장소가 정적 HTML이므로 시안에서도 같은 계산을 실행하고 테스트할 수 있다. 대안인 즉시 전체 Flutter/서버 구축은 인증·영속성·기기 환경까지 한 이슈에 결합하므로 후속 단계로 분리한다. JavaScript 선택이 전체 서버·모바일 스택 확정을 뜻하지는 않는다.

원화는 0 이상 안전 정수. 금액 누적도 안전 정수 이내여야 한다. 비례 곱셈은 BigInt로 처리하여 큰 금액에서 반올림 오류가 생기지 않게 한다. 사용자·차수·입금 ID 중복과 유효하지 않은 값을 거부한다. 입력을 변경하지 않는다.

## 공개 인터페이스

`splitEven(amount, userIds)` → 사용자 ID 고정 정렬로 원 단위 잔여를 1원씩 배분한 `{userId, amount}[]`. 0원/0명은 빈 배열, 양수/0명은 오류.

`splitProportionally(amount, weights)` → `{allocations, remainder}`. 각 개인 비례 몫을 원 단위 절사하고 나머지를 반환한다. `weights`는 `{userId, amount}[]`, 같은 ID 중복은 오류. 이 함수의 나머지는 정책상 초과 취소비 환불에서만 적립에 연결한다.

`calculateCancellation({paid, fee})` → `{charge, refund, outstanding}`. 예 30,000원 납부·비용5,000원이면 환불25,000/미납0. 미납자는 비용만 청구한다.

`settleRound({id, expense, attendeeIds, cancellations})` → 차수 분담·취소 의무·취소 초과금 환불·원 단위 적립·0명 주최 부담. cancellation 항목은 `{userId, fee, received}`이며 received는 실제 확인해 비용에 충당한 금액(0≤received≤fee). 원래 선납 전체와 혼동하지 않는다. 미수령 비용은 참석자 부담에서 빼지 않지만 취소 당사자의 청구 의무에는 남긴다. 초과금은 실제 수령자 비율로 환불한다.

`settleEvent({hostId, rounds, receipts, refunds})` → `{rounds, positions, totalExpense, pendingCancellation, reserveRemainder, hostContribution}`. 입금·환불 항목은 `{id, userId, amount, confirmed}`. false는 잔액에 반영하지 않는다. true만 순입금에 반영한다. position은 `{userId, obligation, received, refunded, net, additional, refund}`. `net=obligation-received+refunded`. 주최자 자기 부담은 계산 근거이며 자기 계좌로 송금하라는 명령이 아니다.

## 불변식과 예제

- 차수 의무 합계 + 주최 부담 = 지출 + 미수령 취소 의무 + 원 단위 적립.
- 참석자 0명도 계산 가능. 0명 분배만 생략하며 지출에서 수령 비용을 뺀 양수는 주최 부담.
- 확인 전 입금은 무시한다. 입금/환불 ID 중복은 거부한다.
- 한 이벤트의 모든 차수를 개인별로 합산, 기지급 환불을 반영한다. 차수별 추가 요청·환불을 중복 생성하지 않는다.
- 지출100,000·비용수령20,000·참석4명이면 1차20,000씩. 2차40,000/4=10,000씩. 각40,000 납부면 최종 각10,000 환불.
- 같은 비율3명에게 초과취소비10,000 환불이면 각3,333, 적립1. 주최자 귀속은 해산 정책이며 일반 정산 초과금에 적용하지 않는다.
- 이미 10,000 환불한 사람의 원래 환불10,000은 재계산 시0. 원본 보존/정정 저장은 #13에서 구현한다.

## 이번에 하지 않는 일

실계좌 조회·송금·로그인·서버 권한·DB·푸시·실제 인계 상태 전이는 구현하지 않는다. 계산기는 외부 거래를 실행하지 않는다. 입력값의 서버 진실성은 후속 API 계층의 책임이다. 임의 개인별 조정 UI는 합계 보존 계약을 확정한 뒤 추가하며 이번 API에는 넣지 않는다.
